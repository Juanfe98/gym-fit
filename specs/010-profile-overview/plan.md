# Implementation Plan: User Profile Overview Page

**Branch**: `010-profile-overview` | **Date**: 2026-05-29 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/010-profile-overview/spec.md`

## Summary

Replace the existing `/profile` settings screen with a modern fitness dashboard overview. The page reads from 5 new Supabase tables (fitness preferences, equipment, body info, limitations, body measurements) via 5 parallel TanStack Query reads, displays 8 section cards with data-or-empty-state rendering, and provides navigation CTAs to 7 stub destination routes. All new tables have RLS. No new npm dependencies required.

## Technical Context

**Language/Version**: TypeScript (strict), React 19, Next.js 15+ App Router
**Primary Dependencies**: Supabase client, TanStack Query v5, Zustand, Tailwind CSS v4, existing i18n system
**Storage**: Supabase Postgres — 5 new tables via migration `006_user_fitness_profile.sql`
**Testing**: Manual verification at 375px and desktop; `npm run build` for type correctness
**Target Platform**: Web (Vercel), primary at 375px mobile viewport
**Project Type**: Next.js web application (authenticated route group)
**Performance Goals**: All 8 sections visible within 2s on standard connection; 5 TQ queries fire in parallel
**Constraints**: No new npm dependencies. No custom backend server. RLS on all new tables.
**Scale/Scope**: Single user per session. 5 Supabase reads per page visit (cached by TQ).

## Implementation Phases

### Phase A — Database (migration)

**Goal**: 5 new tables with RLS live in Supabase. No frontend yet.

1. Create `supabase/migrations/006_user_fitness_profile.sql`
2. Define all 5 tables with constraints and defaults (see `data-model.md`)
3. Enable RLS and create `auth.uid() = user_id` policies on all 5 tables
4. Push migration: `supabase db push`
5. Verify: each table exists in Supabase dashboard, RLS is active

**Validation**: `supabase db push` exits 0. Confirm tables and policies in Supabase dashboard.

---

### Phase B — Types + Service Layer

**Goal**: TypeScript types and all Supabase read functions. No UI yet.

1. Create `src/modules/profile/types/index.ts` — all types from `data-model.md`
2. Create `src/modules/profile/services/profile-service.ts` — 5 read functions:
   - `getPreferences(userId)` — `.from('user_fitness_preferences').select('*').eq('user_id', userId).maybeSingle()`
   - `getEquipment(userId)` — `.from('user_equipment').select('*').eq('user_id', userId).maybeSingle()`
   - `getBodyInfo(userId)` — `.from('user_body_info').select('*').eq('user_id', userId).maybeSingle()`
   - `getLimitations(userId)` — `.from('user_limitations').select('*').eq('user_id', userId).order('created_at')`
   - `getLatestMeasurement(userId)` — `.from('user_body_measurements').select('*').eq('user_id', userId).order('measured_at', { ascending: false }).limit(1).maybeSingle()`
3. Create `src/modules/profile/utils/format-enums.ts` — `FITNESS_GOAL_KEYS`, `EXPERIENCE_LEVEL_KEYS`, `EQUIPMENT_PRESET_KEYS`, `DAY_SHORT_KEYS` maps
4. Create `src/modules/profile/utils/completion.ts` — `calcCompletion()` pure function

**Validation**: `npm run build` — no TypeScript errors.

### Phase C — i18n Keys

**Goal**: All user-visible copy added to `src/i18n/ui.ts` for both `en` and `es`.

Key groups to add:
- Profile overview page: title, edit action
- Completion tiers: `profileCompletionGettingStarted`, `profileCompletionAlmostReady`, `profileCompletionProfileReady`
- Each section title and empty state (title + body + CTA): goal, level, availability, equipment, body info, limitations, measurements
- Goal labels: `goalBuildMuscle`, `goalLoseFat`, `goalIncreaseStrength`, `goalImproveEndurance`, `goalGeneralFitness`, `goalBodyRecomposition`
- Goal personalisation explanations: 6 keys
- Level labels: `levelBeginner`, `levelIntermediate`, `levelAdvanced`
- Level explanation: 3 keys
- Equipment preset labels: `presetFullGym`, `presetHomeGym`, `presetBodyweight`, `presetCustom`
- Body info format: `bodyInfoFormat` → `"{height} · {weight}"`
- Equipment preview more: `equipmentMore` → `"+ {count} more"`
- Limitations count: `limitationsCount` → `"{count} limitations"`
- Measurements entry: `measurementsLatest` → `"Latest: {date}"`
- Error: `profileErrorTitle`, `profileErrorBody`, `profileErrorRetry`

**Validation**: No missing key warnings at runtime. Both `en` and `es` have all keys.

---

### Phase D — Hooks

**Goal**: `useProfileOverview` hook wiring all 5 TQ queries.

1. Create `src/modules/profile/hooks/use-profile-overview.ts`
2. Use `useQueries` (TanStack Query v5) — all 5 queries parallel. `useQueries` is chosen over 5 separate `useQuery` hooks because the page needs a single combined `isLoading`/`isError` state and a single `refetch` for the error retry button. Individual hooks would require manual `&&` chaining and expose no clean retry surface.
3. Derive `isLoading`, `isError`, `refetch` from combined results
4. Map raw DB rows to domain types using service functions
5. Return `{ isLoading, isError, data: ProfileOverviewData | null, refetch }`

**Validation**: Hook returns correct shape. `npm run build` passes.

---

### Phase E — Section Components

**Goal**: All 8 presentational section components + skeleton + error. No routing wired yet.

Build in this order:

1. `SectionCard` — shared card shell: `title: string`, `children: React.ReactNode`. No action slot — each section owns its own action rendering to avoid forcing a union type that breaks dual-action sections (e.g. `MeasurementsSection`)
2. `ProfileSkeleton` — 8 pulsing card placeholders matching final layout
3. `ProfileError` — error message + retry button (`onRetry: () => void`)
4. `ProfileHeader` — avatar/initials, name, completion tier badge, edit link
5. `GoalSection` — goal label + explanation or empty state
6. `ExperienceLevelSection` — level label + explanation or empty state
7. `AvailabilitySection` — days/duration summary + preferred days or empty state
8. `EquipmentSection` — preset + item preview (max 3 + N more) or empty state
9. `BodyInfoSection` — height + weight in preferred units or empty state
10. `LimitationsSection` — count + area preview (max 3) or empty state
11. `MeasurementsSection` — date + key values preview + two actions or empty state

Design rules for all section components:
- Use existing design tokens: `card-elevated`, `gym-text`, `gym-muted`, `gym-accent`, `gym-border`
- Empty states: icon + heading + body text + CTA button/link
- All copy via `t()` — no hardcoded strings
- No hover-only interactions
- All links use `<Link href="...">` from `next/link`
- Min tap target 44×44px on all interactive elements

**Validation**: Each component renders in isolation with mock props. `npm run build` passes.

---
